# ESP Online Tester

Use the running platform at `web/platform/index.html` (workbench) or `web/platform/embed.html` (embedded view). The host serves static assets; firmware executes in the browser's WASM worker. Do not start a separate remote emulator or assume that a 3D preview proves firmware execution.

Read [the API reference](references/api.md) for commands and [configuration and catalogs](references/configuration.md) when constructing scenes or adding products/accessories/firmware.

## Establish the actual device state

Use the page's `window.espTester`, wait until it exists, then read `version`, `capabilities()` and `observe()`. Version `1.0.0` is implemented. Methods are asynchronous except `subscribe`; failures reject with `error.code`, `error.message` and sometimes `error.details`.

Preserve the user's selected model, accessory revision and firmware. StopWatch, PaperMono/Lite and Cardputer-Adv have partial executable board models. PaperMono official 1.2.0 display, brightness buttons, touch, FAT32 mounting/directory reads and RGB digital outputs are verified; Full PaperMono has an ST25R3916 reader digital subset: fixed UserDemo 1.2.0 detects Pro and completes A/B/F/V scans with NO CARD when no peer exists; Lite has no NFC and selects the Lite layout. Full PaperMono also has an SX1262 digital subset: fixed UserDemo 1.2.0 initializes, sends Hello!, and displays Rx PEER only after an explicit matching virtual-peer packet. This does not emulate real RF propagation. Cardputer-Adv official v0.3 boots with a real display and TCA8418 matrix keyboard; Enter leaves the boot screen, physical comma/slash keys navigate its launcher. Its menu entries do not establish complete app compatibility. Other products must be checked through capabilities, never inferred from the ESP32 family. `configure()` success establishes configuration validity; it does not establish firmware compatibility.

For a user-provided remote firmware, use `{manifestUrl, sha256?}` or `{url, sha256?}`. A remote raw BIN is checked as a complete merged image first; a validated ESP application-only image can use experimental application-direct startup. Its source gains `bootMode:'app-direct'` and the pinned SHA-256, both retained in history and share links. This bypasses the bootloader without inventing a partition table; storage initialization, firmware startup and guest resets may still fail. Explicit `bootMode:'rom'` requires a merged image. Never interpret this fallback as verified firmware compatibility. For a local ESP-IDF app, load `{format:'build',files}` with browser Files for `flasher_args.json` and every referenced image; preserve directory paths if names collide. The loader validates chip, offsets, overlaps and partition layout rather than guessing an app address. Cross-origin downloads require CORS. A GitHub repository page is not a binary URL. Do not silently substitute a demo when the requested firmware fails.

Dial K130 / K130-V11 expose physical GPIO42 front press, A41/B40 quadrature encoder and FT3267 single-contact touch through separate `dial` / `dial-v11` identities. K130-V11 official UIFlow2 v2.5.3 boots offline and responds to rotary and touch input; its factory EasyLoader resource also passed LCD-test inputs, but the EXE remains a reference because the web loader does not unpack that container. RTC/RFID, RGB supply, PWM backlight, sound and power/sleep remain outside the verified subset. See `docs/platform/dial-v11-runtime.md`; do not treat a source download or successful API input receipt as complete compatibility.

AtomS3-Lite C124 uses its own `atoms3-lite` board, GPIO41 active-low `button` and one GPIO35 RMT-driven RGB LED. Read `observe().leds`; it has no framebuffer. UIFlow2 v2.5.3 boots with a blue status light; the extracted factory image boots and counts presses, but its public EXE remains a reference because the loader does not unpack it. Software GPIO bit-bang, IR reception, analog power/reset and external Grove routing are not implemented. See `docs/platform/atoms3-lite-runtime.md`.

Writable Flash persists separately for each device and initial firmware content hash. Inspect `observe().storage`; `reset()` retains it. `clearDeviceStorage()` is an explicit destructive action on that scope, restores the original image and leaves the machine ready. Do not clear user data as automatic troubleshooting or test cleanup. Firmware download cache has its own clear action. For tests, use an isolated browser context; portable recording requires pristine storage and never includes private Flash pages.

PaperMono/Lite and PaperS3 also have a virtual TF card: firmware load creates a default 64 MiB FAT32 image, or restores the current product + board + initial full-Flash hash namespace. Inspect `observe().sdCard` and `capabilities().sdCard`. Use `attachSdCard({bytes})` for a complete 1–128 MiB disk image (512 KiB alignment), `exportSdCard()` for `{bytes,filename}`, and `flushSdCard()` to await saving. `clearSdCard()` or `attachSdCard({format:'fat32'})` explicitly replaces this scope with an empty card; both replacement paths preserve Flash and leave `ready`, so call `start()` only when execution is intended. Never clear/import as automatic test cleanup on user data.

The workbench and mini player share these SD controls and API, including iframe RPC. SD autosave scans every 1.5 seconds (`crashSafe:false`); IndexedDB persistence survives normal reload, while memory fallback and uncommitted writes do not. Same-origin cross-page changes stop stale sessions rather than silently merge cards. Private SD content stays out of URLs and recordings; imported or modified cards are not pristine. Read [the SD/RGB API details](references/api.md#virtual-tfsd-cards-and-rgb-output) before handling images or testing storage. Observe `leds` events or `observe().leds` for real firmware RGB output; do not simulate it by manually coloring the mesh.

Full PaperMono exposes a digital SX1262 LoRa subset; Lite does not. Check `capabilities().lora`, inspect `readLoRa()`, and supply an explicit peer with `receiveLoRa(packet)` only when intended. It has no automatic echo, real RF propagation or remote relay. Match the peer's actual channel settings; do not silently copy receiver settings to hide a mismatch. A scheduled-input receipt is not guest consumption: verify FIFO/IRQ-driven firmware output. LoRa inputs are not portable recording events. Read [the LoRa API](references/api.md#virtual-lora-packets) before use.

## Configure, operate, verify

1. Obtain the catalog via `import('./catalog.js')` relative to the platform page. Use `loadCatalog()` and `createDefaultScene(catalog, productId)`; validate with `validateScene(scene,catalog)` before `espTester.configure(scene)`. Inspect warnings, not just `valid`.
2. Unverified or partially compatible catalog firmware may be tried when the target board exists and the image is bootable; preserve the trial label and report actual failures. Do not make per-firmware boot validation a prerequisite for catalog availability. When the task asks only for metadata/default selection or explicitly says not to run firmware, limit work to those checks. `await espTester.loadFirmware()` fetches the scene's source; `await espTester.start()` boots it. Check firmware-specific serial output, a real frame, or another observable condition with a bounded wait. A queued input acknowledgment is not a test pass.
3. Before an action, register a fresh observation: `const result = api.waitFor({serialIncludes:'BUTTON_A',fromNow:true,timeoutMs:15000}); await api.press('button-a'); await result;`. Otherwise old buffered output could make a new action appear successful.
4. Use `capture({format:'png'})` for actual device pixels. `NO_FRAME` means there is no firmware framebuffer; do not substitute the 3D case or a mock screenshot as device output.
5. Record the scene, `(await api.observe()).firmware` artifact receipt, assertions, errors and support limitations. `await api.share({mode:'embed'})` produces a portable scene URL. After local file loading, this API rejects sharing until the firmware is published at a browser-readable URL. The UI can export or share a configuration without local firmware bytes and labels that omission. Pause or dispose task-owned sessions when finished; close task-owned browser resources according to the repository's lifecycle instructions.

For a matrix keyboard, inspect `capabilities().input.keyboard` and the product's `controls`; use `api.press(control.id)` for the same keys exposed by the 3D model. The low-level event is `{type:'matrix-key', row, column, pressed}` with the product's physical row/column coordinates. Do not send typed text through UART to imitate key switches, or infer matrix coordinates from GPIO numbers. Check modifier combinations and release on blur; verify the resulting firmware UI. Catalog key geometry may be available before the corresponding runtime is ready.

Original Cardputer K132 and K132-V11 use board `cardputer` with keyboard model `gpio-matrix-74hc138`; Adv uses `cardputer-adv` and `tca8418`. Original official v1.1 is partially verified through boot, Enter and launcher navigation. Both share physical 4×14 input coordinates, but never substitute one board for the other.

AtomS3 C123 uses board `atoms3`: GC9107 128×128 visible display, GPIO41 active-low Button A, and an MPU6886 polling register subset. Its screen is a physical press button (`btnA`, keyboard A), not a touch panel. Internal source-built firmware verifies pixels, button reads and IMU values; the catalog's official factory firmware remains a trial, not a compatibility certification. Explicit `setImu` agent input is available with virtual axes; `capabilities().imu.sceneOrientation` is false until a model-to-sensor transform is established. Do not substitute this board for AtomS3R, AtomS3-Lite or ST7735 display batches. See the repository's `docs/platform/atoms3-runtime.md` for scope and reproduction.

AtomS3R C126 uses its own `atoms3r` board for the current ST7735 batch: SPI pins differ from AtomS3, LP5562 controls white backlight, GPIO41 screen press is control `button` (keyboard A), BMI270 offers explicit virtual-axis input, and Octal PSRAM is 8 MiB. BMM150 AUX, RGB/IR and old GC9107 panels are still missing; `source:'scene'` is rejected. See `docs/platform/atoms3r-runtime.md`; do not use this board for other S3R SKUs without separate adaptation.


Dial K130 uses board `dial`: GC9A01 240×240 display, FT3267 single-contact touch on I2C11/12, front press GPIO42 and encoder A41/B40. Drag the gray grip ring or call `input({type:'encoder',id:'encoder',steps:1})`; orange front bezel press and touch screen are separate hit surfaces. Positive detents are A-first quadrature and produce -4 counts in the official decoder; physical shaft direction is not hardware-calibrated. RTC/RFID, buzzer/audio, PWM brightness and power latch remain unimplemented. K130-V11 uses the separate `dial-v11` board described above. The factory source/EasyLoader reference remains first; no complete remote BIN was located. See `docs/platform/dial-runtime.md`.

DinMeter K134 uses board `dinmeter`: ST7789V2 240×135 physical landscape, GPIO42 press (`encoder-button`, keyboard A), and A41/B40 encoder (`encoder`). The CAD knob front center presses and the rim drags. A positive input step produces +2 in the official UserDemo half-quadrature PCNT counter, or −4 in the internal full-quadrature decoder; 16 UI detents per turn is a presentation convention, not measured hardware. Fixed official v0.1 menu, display-test and encoder-test output were observed in actual WASM. RTC explicitly NACKs; brightness PWM, battery, buzzer, power/sleep, Grove and networking are incomplete. K134-V11 uses separate board `dinmeter-v11` with ST7789P3 ID 81/81/B3 and button ID `encoder-press`; fixed v0.1 also passed real native/WASM menu and encoder inputs. It retains the same explicit missing-peripheral scope plus the unmodeled Stamp-S3A RGB supply gate. See `docs/platform/dinmeter-v11-runtime.md`. See `docs/platform/dinmeter-runtime.md`.

Stamp-S3 S007 uses board `stamps3`, 8 MB Flash / no PSRAM, GPIO0 active-low `button` (keyboard A), one WS2812B GRB LED on GPIO21 through RMT. Actual official UIFlow2 2.5.3 boots to a blue LED; its full application/network behavior remains unverified and trial. A separate internal IDF fixture verifies 3D cap/keyboard input through guest GPIO and RMT color changes. The retained shield can occlude the photo-estimated LED package. No FPC display, analog power or software-GPIO LED decoding is claimed; PIN variants and Stamp-S3A remain separate. See `docs/platform/stamps3-runtime.md`.

Air Quality K131 uses board `airquality`: SSD1681 200×200 e-paper, GPIO0/8 A/B inputs, SCD40/SEN55 digital I²C and an explicitly fixed virtual environmental profile. The fixed official v0.2.0 image reaches its sensor page; B opens settings and AP setup, A returns. This display is not touch-sensitive. RTC, battery ADC, audio, real Wi-Fi/cloud, power latch/sleep and external Grove are not accepted; preserve the guest’s unsupported values and do not infer real air measurements. K131-V11 remains separate. See `docs/platform/airquality-runtime.md`.
Air Quality v1.1 (`m5stack-k131-v11`, board `airquality-v11`) 保留独立 Stamp-S3A 身份，沿同一官方载板路由；RGB/G38 供电开关仍未模拟，不能据原版验收推定整机兼容。

Use explicit timestamps and values for reproducible GPS tests. Choose `m5stack-gps-u032` (AT6558, default 9600) or `m5stack-gps-u032-v11` (AT6668, default 115200) from the actual hardware revision. The implemented GPS path requires StopWatch and `{mode:'logical',port:'uart1'}`. It injects checksummed NMEA into the emulator's UART1 input and bypasses physical pin routing, baud timing and external power. It does not certify wiring or physical GPS behavior.

Hello and StopWatch diagnostic firmware are internal automated-test fixtures. They are absent from the public catalogs, and the StopWatch diagnostic manifest/binaries are excluded from Pages. Do not offer them as user devices or selectable production firmware. Local repository tests can use `tools/fixtures/platform-catalog.mjs`; diagnostic serial assertions do not apply to official firmware.

On a fresh visit or device change, the workbench selects the first matching firmware; an identified official factory firmware belongs first and is referenced by `defaultFirmwareId`. Preserve an explicit source in a shared scene or a user selection. StopWatch defaults to `m5stack-stopwatch-official` (official User Demo V0.5). When constructing a fresh scene programmatically, resolve the product's `defaultFirmwareId` from the firmware catalog and assign its pinned source; `createDefaultScene` itself leaves firmware null. Simultaneously hold A+B to open/return to the launcher; A/B select a feature, touch opens it. Inside Stopwatch, B starts/stops and A adds a lap while running or resets while stopped. Use guest time when testing holds; a short host delay is unreliable under CPU load. RTC/IMU/audio/power behavior remains partial and no physical hardware validation is implied.

To change only presentation, preserve `observe().scene.view` and call `updateSceneMetadata({view:{...view,appearance:{shell:{color:'#8456cf',opacity:0.36,finish:'plastic'}}}})`. This preserves running firmware and is portable through sharing/embedding. Color is six-digit hex, opacity is 0–1; read `SHELL_FINISHES` from `appearance.js` for the eight supported finish IDs. Omit `appearance` to restore the product's original shell. `UNKNOWN` PCB is a replaceable blank placeholder, not verified internal CAD. Exploded animation remains planned, not an implemented API.

## Record and share interactions

Load a remote firmware source first. `await api.recordingStart()` resets and boots it, then captures only successfully acknowledged button, matrix-key, encoder and touch inputs. A keyboard press records its mapped device button or matrix coordinate; screen taps and left/right drags record normalized down/move/up coordinates. Camera selection/frames, serial/GPS injection, flashing and scripts are excluded. The limits are 120 guest seconds, 500 events and 32 KiB per recording. Local firmware files cannot supply a portable recording source.

```js
await api.recordingStart();
await api.waitFor({port:'uart0', serialIncludes:'[Launcher] on open', timeoutMs:120000});
await api.press('button-a', {durationMs:150}); // Sample input; separately verify its firmware-specific effect.
const recording = await api.recordingStop(); // Releases any remaining held inputs.
const link = await api.share({mode:'embed'}); // Includes scene= and recording=.
const receipt = await api.recordingPlay(recording); // Resets again; compare the receipt.
```

Replay requires the same product, firmware source/hash, accessories and embedded local definitions. It verifies artifact hashes before running. Presentation and keyboard remapping can differ because recorded buttons are semantic. A valid shared scene now loads and starts automatically; an included valid recording replays automatically. Catalog trial firmware still asks the human receiver to confirm once, and unavailable boards never start. Use `api.share({autostart:false})` for configuration-only links or `{autoplay:false}` to run without replay; the equivalent fragment flags are `autostart=0` and `autoplay=0`. Plain visits without a scene remain idle. Automatic replay preserves the pristine-storage requirement: never clear Flash or SD to make it proceed. The workbench shares the current scene without an incompatible old recording and explains the omission; it preserves that recording locally so the original configuration can still be restored. Use `recordingTakeOver()` to cancel and release held inputs before human control; `recordingObserve()` and `subscribe` expose progress. See [recording details](references/api.md#recording-and-replay) for bundle format and timing limits.

Guest-time intervals are preserved using actual worker input acknowledgements. Scheduling still observes the guest clock from the host; this is not cycle-exact or bit-exact replay. Receipts report original/scheduled/actual times, accumulated lateness and a final framebuffer hash comparison. The diagnostic firmware validates touch delivery, not left/right navigation semantics; assert the latter only with firmware that implements them.

## Verification commands

In a local checkout, run `node tools/platform-config-test.mjs` after changing scene, catalog or private accessory handling. Run `node --test tools/platform-sd-card-test.mjs tools/platform-device-storage-test.mjs` for storage boundaries without launching an additional catalog firmware audit. Run `node tools/platform-recording-test.mjs` for recording boundaries and lifecycle; with built WASM/demo assets, `node tools/platform-recording-test.mjs --real --receipt <output.json>` also exercises real firmware A/B short presses, a tap and left/right touch trajectories. The receipt does not claim gesture navigation. Runtime and browser tests are listed in the repository's platform documentation. Follow `AGENTS.md` before a pull request; these checks do not replace required Rust or browser checks.

For third-party embedding, use the origin/session-bound `postMessage` protocol in [the API reference](references/api.md#embedded-parent-control). A cross-origin parent cannot read `iframe.contentWindow.espTester` directly.
