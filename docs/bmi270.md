# BMI270 digital samples and interrupts

`esp_periph::i2c::bmi270::Bmi270` keeps the existing polled sample contract for
boards that do not advance its clock. A board may opt into guest-time sampling
with `advance_to_us(guest_us)`. The CoreMatrix board uses this mode to route
INT1 to PM1 GPIO4, which can wake the main supply while the sensor's L1/LDO
supply remains held. Product wiring and supply handling belong to the board;
this peripheral never restarts a CPU directly.

The model is based on [Bosch BST-BMI270-DS000-08 revision 1.6, March 2026](https://www.bosch-sensortec.com/media/boschsensortec/downloads/datasheets/bst-bmi270-ds000.pdf),
sections 4.6, 4.8.2–4.8.3, 4.9, and 5.2.40–5.2.63, and the
[Bosch SensorAPI at 41129fc](https://github.com/boschsensortec/BMI270_SensorAPI/tree/41129fcfe39c583ee5462d79195741945d51c1fe).
The [M5Unified BMI driver at b67ea7b](https://github.com/m5stack/M5Unified/blob/b67ea7bd2d187d3fa8719edf1b915fd34a128c0d/src/utility/imu/BMI270_Class.inl)
uploads the 8 KiB configuration, enables the sensors and reads INT_STATUS_1
before reading the vectors. That pinned driver does not use a FIFO.
Exact source URLs, final URLs, fetch times, sizes, media types and SHA-256 are
recorded in [the source receipt](platform/evidence/corematrix-imu/sources.json).

## Board interface

- `advance_to_us(us)` advances only forward in the guest clock domain. Host
  inputs are held between changes. Advance to a change's timestamp before
  replacing the shared `Bmi270Sample`, then let the next sensor tick sample it.
- `next_deadline_us()` identifies the next data sample, motion-engine sample
  or IRQ pulse expiration. A board must service these deadlines to observe
  transient output edges; a large jump retains status but cannot reconstruct
  output transitions already in the past.
- `interrupt_pins()` returns INT1/INT2 as `[Option<bool>; 2]`. `Some` is a
  driven level. `None` is output disabled or released open drain. Resolve it
  through the board's actual pull or release the receiving input; never treat
  an unconnected pin as automatically high.

The digital clock uses quarter-microsecond units, representing the 3200 Hz
sample period and 1/6400 second IRQ pulse without cumulative period rounding.
The public microsecond deadline rounds up by at most 0.75 microseconds.
Sampling and power-setting writes reset the relevant scheduling epoch;
startup/filter settling and oscillator tolerance are not modeled. Long time
jumps use bounded arithmetic, not an unbounded per-sample loop.

## Implemented register behavior

| Registers | Behavior |
| --- | --- |
| `0x40`, `0x42`, `0x7D` | ACC/GYR ODR and power gate data-ready generation after successful initialization. Unsupported ODR codes schedule nothing. |
| `0x03` | Data-ready flags for current vectors. In guest-clock mode reading any corresponding vector byte clears its flag. Existing polling boards retain their full-vector clearing behavior. |
| `0x1C`, `0x1D` | Feature/data status is sticky until read. A still-active latched feature condition reasserts after the read. |
| `0x53`, `0x54` | Output enable, active high/low and push-pull/open-drain INT1/INT2 behavior. |
| `0x55` | Latched mode retains the pin until status is read; non-latched data-ready lasts 156.25 microseconds. Feature pins follow the active condition. Status stays sticky in either mode. |
| `0x56`, `0x57`, `0x58` | Feature and data-ready interrupt routing to either pin. Unmapped events do not drive that pin. |
| `0x2F`, `0x30..0x3F` | Eight separate feature pages. Standard-profile ANYMO is page 1 at `0x3C..0x3F`; NOMO is page 2 at `0x30..0x33`. |
| `0x7E=0xB6` | Software reset clears interrupt state/configuration and feature configuration, retaining the caller's forward clock domain. |

The vector read snapshot is captured at the read address phase, so a sensor
tick during a multi-byte I2C/SPI read cannot mix two samples. Data-ready is
periodic even if the host sample version is unchanged. Existing untimed boards
still generate their polled ready event on host version changes.

## Motion subset

Any-motion and no-motion use the standard Bosch feature-page fields:
13-bit duration, X/Y/Z selection, 11-bit threshold in 1/2048 g, output-bit
selection and feature enable. The reference and counters run at 50 Hz;
duration zero still requires a qualifying sample. High-performance filter mode
permits the feature engine independent of output ODR; low-power mode requires
at least 50 Hz, per the datasheet. The host samples are bounded to the selected
acceleration range, and nonfinite selected-axis values cannot assert motion.

Any-motion compares each selected axis with the reference held since the last
assertion. A threshold exceedance for the configured consecutive duration
asserts the chosen feature bit and updates that reference, following datasheet
Figure 1. The non-latched condition clears when the new slope falls below the
threshold. No-motion counts samples below threshold on all selected axes and
updates its reference when that condition fails. A continuing stationary
condition reasserts a latched no-motion IRQ after status is read.

These are digital threshold/sequence models. They do not execute Bosch's
uploaded feature-engine code, reproduce analog filtering/noise or claim
physical motion calibration. The complete 8 KiB upload is still checked for
coverage before initialization succeeds; its bytes are retained but are not
interpreted as executable code. Different Bosch configuration profiles,
feature-axis remapping, significant motion, step counting, wrist gestures,
FIFO/watermarks, auxiliary magnetometers, sensor time and self-test remain
outside the implemented subset. Unknown feature pages are register storage,
not evidence those algorithms execute.

## PM1 input resolution

CoreMatrix's INT1 connection requires the existing PM1 device to distinguish a
driven low from high impedance. `M5pm1State::release_input(pin)` now removes the
external driver and resolves PM1 GPIO pull configuration. A floating input is
unknown for edge detection; it cannot invent a falling wake edge. A configured
pull-up followed by a real open-drain low produces the expected edge. GPIO
output mode retains priority over input observations. The legacy StopWatch
GPIO2 charging-status fallback remains unchanged; details are in
[M5 I2C devices](m5-i2c.md).

## Verification

Run:

```sh
cargo test --release -p esp-periph --lib i2c::bmi270
cargo test --release -p esp-periph --test m5_i2c
cargo clippy -p esp-periph --all-targets -- -D warnings
```

Tests cover the existing polling/SPI contract, bank isolation, ODR/power and
mapping boundaries, IRQ pulse/latch/polarity/drive behavior, atomic vectors,
any/no-motion duration and axis selection, low-power rate constraints, reset,
floating/pulled PM1 inputs, and a real BMI270 INT1 → PM1 GPIO4 wake chain.
No test writes a framebuffer or fabricates a firmware interrupt receipt.
These protocol tests do not establish full CoreMatrix firmware or silicon
compatibility; that requires the board and firmware run evidence.
