No firmware, NVS, ROM instruction or eFuse calibration is changed.

HP initialization is `0x42003452`–`0x42003730`, LP initialization `0x42003732`–`0x42003856`, and the enclosing application `pmu_init` is `0x42003858`–`0x42003a6c`. The retained pre-integration exception established only the first store. The parameter audit below is static evidence; the later parent checkpoint separately records130 actual PMU writes.

Each HP table has 13 words and stride `0x34`. `pmu_init` programs ACTIVE, MODEM and SLEEP tables in order, then two LP tables, then removes startup force overrides:

| HP word offset | Meaning | Owner |
| --- | --- | --- |
| `+0x00` | digital power targets | BootPmu |
| `+0x04`, `+0x08` | functional/APB ICG targets | BootPmu |
| `+0x0c` | modem clock code | Existing BootAnalog for ACTIVE; BootPmu for future MODEM/SLEEP |
| `+0x10`, `+0x14`, `+0x18` | system controls, clock power, bias targets | BootPmu |
| `+0x1c`, `+0x20`, `+0x24` | retention/backup, backup clocks, system-clock targets | BootPmu |
| `+0x28` | HP regulator target | Existing BootBias for ACTIVE/MODEM; BootPmu for future SLEEP |
| `+0x2c`, `+0x30` | regulator driver, XTAL targets | BootPmu |

The C5 LP table at `+0x9c` is `lp_sys[LP_ACTIVE]`, despite historical HP_SLEEP naming in the register header. It uses the existing BootBias `+0x9c` and BootAnalog `+0xac`, plus new `+0xa0/+0xa8`. LP_SLEEP uses `+0xb4/+0xb8/+0xbc/+0xc0/+0xc4/+0xc8`. The LL explicitly writes XTAL and bias to LP_SLEEP even during the LP_ACTIVE loop. `+0xa4/+0xb0` are reserved WT words and are not part of this subset. Every HP loop still executes the existing `+0xdc/+0xd0` update commands and sets `SLEEP_PRT_SEL=2` in `+0x130`; those updates do not select the future MODEM or SLEEP power tables.

The cleanup RMW sequence clears FORCE_PU2, FORCE_NO_RESET3, FORCE_NO_ISO4, FORCE_PD5, FORCE_ISO1 and FORCE_RESET0 for TOP/HPAON/CPU/WIFI/LP_PERI (`+0xf8/+0xfc/+0x100/+0x108/+0x10c`), with full header POR `0x1c`, then clears MEM_NO_ISO27:24 in `+0x110`, POR `0xff000000`. The reserved HP domain3 at `+0x104` is not accessed by this source sequence and remains unknown here. The final memory word is `0xf0000000`, preserving FORCE_MEM_PU31:28. Deasserting a force override while the supported awake targets remain powered does not claim a power transition or SRAM retention cycle.

[registers.json](registers.json) enumerates all 51 exact new word addresses, complete C5-header POR values, named RW masks and functional policies. There is no contiguous PMU register RAM fallback. Existing BootAnalog and BootBias addresses remain single-owned; no second copy of `+0x0c/+0xac/+0xcc/+0xd0/+0xdc/+0x28/+0x5c/+0x9c` is added. The new module does not expose live-state, ready, wakeup-status or calibration registers.

The supported profile is explicitly awake. ACTIVE digital power targets must remain 0; any requested SPI/memory/WiFi/peripheral/CPU/AON/TOP power-down rejects transactionally. ACTIVE functional/APB ICG words remain all 1, system control remains 0, and XTAL remains 1. ACTIVE clock-power, bias and system-clock targets permit only their unchanged initial configuration or the source's safe enable values `0x70000000`, `0x02000000` and `0x08000000`; a later clear, isolation/retention request, watchdog pause, CPU stall, pad hold or analog driver change rejects. These target words are not used to manufacture live PLL readiness or change the existing PCR clock engine. Immediate commands remain the responsibility of their original owner, and newly unimplemented commands reject.

MODEM/SLEEP tables retain named configuration without executing those states. Their programmed CPU power-down, stall, pad-sleep or oscillator-off values do not affect the current awake CPU, memories, clocks, GPIO or watchdogs. Backup and retention enable bits reject even in future tables, since their engines are absent. The format/mode fields themselves can be stored without an execution claim. Force controls only clear already asserted POR overrides and cannot assert new reset/isolation/power-up/power-down overrides; memory control only clears NO_ISO. Sleep-protection selection is a configuration field; sleep requests at `+0x124`, LP CPU sleep/wake commands, new IMM triggers and actual state transitions remain unknown/rejected.

TRM13.4.2 explains that these per-state targets control regulators/clocks/power when a corresponding PMU state is selected, and that PCR retains clock-gating control when ICG_SLP_SEL=0. The awake subset deliberately permits only safe unchanged/enable targets and rejects requests whose current physical effects are absent. It does not establish a measured regulator supply, analog settling, sleep transition, power-domain isolation, RAM loss or retention execution. The header names a peripheral power-down bit28 where `pmu_struct.h` leaves that bit reserved; ACTIVE rejects it with every other power-down, and a future-table stored named field is not a claim that a physical transition was verified. Several regulator fields are also reserved in the TRM but named by the pinned C5 IDF header; this earlier documented disagreement is preserved.

`BootBias::write` retains its original strict behavior and six regression tests. The additional `write_awake_config` entry is selected only by the validated-ROM integration path. It permits HP sleep-memory/logic XPD16/17 and sleep DBIAS22:19/26:23, plus LP sleep XPD21 and sleep DBIAS26:23. Main regulator XPD remains 1, sleep-connect15 is preserved, PMU selector14 remains 1, and INIT3/PVT handoff stay rejected. The actual sequence ends at ACTIVE `0xe004f9c0`, MODEM `0xe0048000`, LP_ACTIVE `0xe0400000`; RO codes still derive from actually written HP/LP targets 28/28, with no voltage claim.

The ACTIVE analog parameter blob contains INIT=1 and literal RO fields HP28/LP13, but `pmu_hp_system_init` does not call setters for INIT, RO fields, selector or sleep-connect. The typed instructions preserve those fields instead of writing the blob wholesale. Consequently INIT remains 0, selector remains 1, sleep-connect remains its existing 1, and RO is not seeded to LP 13. The targets 28 come from the guest's unchanged `get_act_*_dbias` calculation on the existing uncalibrated eFuse profile, not from host initialization.

BootAnalog's existing `+0xac` stores XTAL32K power-request28 so the actual LP_ACTIVE default can become `0x50000000`. It creates no crystal signal, ready flag or 32kHz source; existing clock selection/calibration still sees no XTAL32K input. FOSC30 continues to feed the existing 17.5MHz RC_FAST model through its actual pure getter. RC32K29 and slow-OSC power-down31 remain unsupported. The private PLL helper is the sole storage location; no duplicate oscillator or PLL engine is added.

CPU/Core reset preserves this PMU configuration; explicit LP/System or Chip reset restores complete header defaults. This follows the existing declared PMU/Bias functional domain contract. The public fields do not specify every per-flop reset-retention detail, so this is not measured silicon retention or asynchronous cycle accuracy. There is no per-tick work, deadline, IRQ, completion bit or physical voltage model in BootPmu.

After these configuration calls, the original power-on path calls `esp_ocode_calib_init`. Existing chip revision 100/block revision 0 selects `calibrate_ocode`, not a manufactured calibrated eFuse code. Its real flow calibrates a slow-clock period, saves CPU clock configuration, switches to XTAL, issues I2C_ULP `0x61` reset commands, polls O_DONE/BG_DONE or timeout, then restores clocks. That analog engine is outside this change. Its unimplemented target/commands remain real access boundaries; no constant DONE, calibrated byte, forged eFuse provisioning or skipped call is supplied. Enabling PVT or actual sleep likewise requires separate engines.
