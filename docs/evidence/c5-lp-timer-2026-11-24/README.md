## Source and module scope

The unchanged LCD273 factory baseline stops at bootloader PC`0x4084efac`, reading LP_TIMER_UPDATE`0x600b0c10`:796274 instructions,796224 nominal cycles,1353 UART bytes and zero pixels/SD commands. The bootloader has printed the partition table, selected the factory image and announced app segment0 mapping at paddr`0x20020`, vaddr`0x42130020`, size1904700. That baseline alone does not prove the map completed. The standalone module change added only the software-capture path; the later integrated rerun is described above.

Sources are fixed IDF v5.5.3`2c211b236707889e8400c4dc5644dd5c4ee071e0`, matching the factory, compared against v5.5.4`735507283d5b2f9fb363a1901172dbd9e847945d`. The C5 [register header](https://github.com/espressif/esp-idf/blob/2c211b236707889e8400c4dc5644dd5c4ee071e0/components/soc/esp32c5/register/soc/lp_timer_reg.h), struct, [LL](https://github.com/espressif/esp-idf/blob/2c211b236707889e8400c4dc5644dd5c4ee071e0/components/hal/esp32c5/include/hal/lp_timer_ll.h), [HAL](https://github.com/espressif/esp-idf/blob/2c211b236707889e8400c4dc5644dd5c4ee071e0/components/hal/lp_timer_hal.c) and C5 rtc_time.c are byte-identical between those versions. The C5 reg_base header puts LP_TIMER at`0x600b0c00`.

The typed original bootloader sequence at`0x4084ef9e..0x4084efc4` matches `lp_timer_hal_get_cycle_count`: load the LP_TIMER context, read UPDATE+10, OR`0x08000000`, write it back, read buf0 low+14/high+18, mask high to16 bits and return. The LL writes MAIN_TIMER_UPDATE bit27; the HAL then reads the captured data directly. C5 has no VALID field or ready-poll protocol in these sources. The model adds none. UPDATE is WT, reads zero with all automatic event selectors disabled, and performs a real capture before the accepted command returns. This is a synchronous functional capture, not a claim about analog/CDC/APB latency.

[C5 TRM1.1](https://documentation.espressif.com/esp32-c5_technical_reference_manual_en.pdf), chapter17, describes a free-running48-bit counter, software-triggered logging and the two most recent captures. Each accepted WT27 copies the prior buf0 to buf1 and the actual current counter to buf0. The four RO capture words preserve their values while the live counter continues; reads do not capture again. High words expose exactly16 bits. Counter rollover is modulo2^48 and computed arithmetically, with an aggregate diagnostic wrap count. Overflow IRQ registers remain unsupported; no interrupt-enable or alarm command is accepted without its engine.

The implemented addresses are only base+10/14/18/1c/20. Automatic REGDMA/XTAL/stall/reset logging selectors28–31, reserved UPDATE bits, targets/alarms, IRQ/ETM/sleep control, alarm-load and all other addresses reject. Writes to the four documented RO capture words are ignored. There is no generic register RAM, guessed older-chip alias or constant ready flag. The TRM17.3 prose accidentally names BUF1_HIGH in its group0 pair; the register table, fixed headers/struct and actual instructions agree on BUF0_HIGH at+18, which is used here.

The counter has no software EN field. DATE.CLK_EN31 resets0 and controls automatic versus forced register clocking according to TRM register17.18; it does not disable the free-running counter. DATE access is outside this narrow subset. The independent LP_CLKRST_LP_RST_EN at+0c, bit29, can reset LP_TIMER and resets0. That unimplemented control must continue to fault on writes; this subset assumes its released POR state. LP_CLKRST_CLK_TO_HP+20 bit29 only sends RC_SLOW to the HP system and must not gate the LP counter. No independent counter gate was found in the fixed C5 LP_TIMER header/LL.

The timer receives `set_slow_clock(cycle,Option<hz>)` from the actual clock owner, with no fixed136kHz fallback. TRM17.3 names RC_SLOW, while the clock table9.2-6 and system-timer sleep-time conversion also refer to LP_DYN_SLOW/RTC_SLOW. The supported board profile is restricted to the actual RC_SLOW selection and DIG DCAP128 configuration represented by BootClock's existing getter; alternate sources and physical source-mux transients are outside this model. A missing/unknown observation freezes model count and phase; it does not reconstruct uncalibrated cold-prefix ticks. Snapshot with no source rejects before any mutation, so it cannot manufacture a current time of zero. Prior captured words remain readable.

The host must create/select this counter at the validated cold epoch, before the actual DCAP clock becomes known, and notify source changes at their actual boundaries. Creating the timer only on its first MMIO would lose known elapsed time. `set_slow_clock` first integrates the old rate, then publishes the new one, preserving fractional source ticks. The model uses the existing nominal240MHz scheduler, integer arithmetic and constant work even over u64 maximum elapsed time. Virtual epoch0 is an explicit initial/reset profile, not a measured silicon absolute uptime or an invented replacement for an unknown source. The report includes its last integrated cycle.

The API is `LpTimer::new(cycle)`, `enable_virtual_profile(cycle)`, `disable_virtual_profile()`, `virtual_profile_enabled()`, `contains(address)`, `set_slow_clock(cycle,Option<hz>)->bool`, `pump(cycle)`, absolute-address `read_at(address,cycle)->Option<u32>` / `write_at(address,value,cycle)->bool`, `reset_domains(cycle,lp,analog)` and `report()`. Strict profile-off behavior faults and has no autonomous counter work. Profile reselection retains history; deselection withdraws the source without backfilling a hidden interval later.

TRM17.2 describes uninterrupted operation across HP resets, with LP-system power-on as the exception;17.3 explicitly excludes LP system reset from continuous counting. The bounded reset contract therefore preserves counter, phase and capture words across CPU/Core reset. LP/System reset clears counter/captures to virtual epoch0; supplied source observation is retained for the clock owner to refresh. Chip/analog reset also removes the source observation, which remains None until actually configured again. Automatic reset logging is not enabled, so no reset capture is invented. The owner arbitrates earlier watchdog events before advancing this timer and passes the actual reset timestamp; the module does not roll back arbitrary already-committed timelines or retired instructions.
