# StamPLC runtime subset

K141 has an independent `stamplc` board with ESP32-S3, 8 MB Flash and no PSRAM. It follows the official v1.0 CPU/IO schematics and the pinned M5StamPLC-UserDemo driver. Its existing factory image remains the first/default firmware; the product remains `partial` and the image remains `trial`, `simulationVerified:false`. [Product](https://docs.m5stack.com/en/core/StamPLC), [CPU schematic](https://m5stack-doc.oss-cn-shenzhen.aliyuncs.com/1129/K141_sch_StamPLC_V10_CPU.pdf), [IO schematic](https://m5stack-doc.oss-cn-shenzhen.aliyuncs.com/1129/K141_sch_StamPLC_V10_IO.pdf).

The ST7789V2 receives actual SPI2 writes through MOSI8, SCLK7 and CS12, with DC6 and reset3. The fixed landscape glass is 240×135. The manufacturer's M5GFX configuration starts from a 135×240 panel with offsets52/40 and rotation offset1; the resulting landscape address window starts at column40/row53 with MADCTL0x64. The model maps that window to the physical glass and checks all 32,400 pixels, including four distinct corners. LCD identity/GRAM reads, analog initialization delays and optical calibration are not implemented. No static image substitutes for guest pixels. [Factory display driver](https://github.com/m5stack/M5StamPLC-UserDemo/blob/7fc748c3b18b7092cc482bce02c4495d3d9322e4/platforms/esp32s3/main/hal_stamplc/components/hal_display.cpp), [M5GFX rotation calculation](https://github.com/m5stack/M5GFX/blob/65c816a38386062d2c3dc47d41237a9083acbc75/src/lgfx/v1/panel/Panel_LCD.inl).

Both expanders use SDA13/SCL15, share active-low IRQ14 and reset3, and respond through the same hardware-controller or bit-banged I2C routes. PI4IOE5V6408 address0x43 reads A/B/C on P2/P1/P0. A pressed key pulls its input low; release lets the guest-configured internal pull-up determine the level. They are semantic `button-a`, `button-b`, `button-c` controls, never substituted ESP GPIO0 inputs. PI4IO P6/P5/P4 drive front R/G/B and P7 drives backlight, all active-low. Direction and high-impedance settings gate the outputs. These are binary digital levels, not an analog brightness model. [Factory expander A driver](https://github.com/m5stack/M5StamPLC-UserDemo/blob/7fc748c3b18b7092cc482bce02c4495d3d9322e4/platforms/esp32s3/main/hal_stamplc/components/hal_io_expander_a.cpp).

AW9523B is address0x59 (AD1=0, AD0=1). The model respects its address-dependent reset output bytes0x0f/0x0f, input/output direction, GPIO/LED mode and P0 open-drain selection. A reset high output is released, so it does not energize the relay driver. P0.0–3 drive ULN2003 inputs only after guest configuration enables actual high drive. Guest input reads observe those digital outputs. The eight optocoupler inputs stay at their disconnected pull-down level0; external voltage stimuli, optical thresholds, relay contacts and loads are not modeled. Input-port interrupt read-clear/masking has a focused protocol test; no host optocoupler injection API is advertised. [AW9523B datasheet v1.1.1](https://m5stack-doc.oss-cn-shenzhen.aliyuncs.com/1129/AW9523B.pdf), [factory expander B driver](https://github.com/m5stack/M5StamPLC-UserDemo/blob/7fc748c3b18b7092cc482bce02c4495d3d9322e4/platforms/esp32s3/main/hal_stamplc/components/hal_io_expander_b.cpp).

Visible LED index0 is the front binary RGB. Index1 is the internal Stamp-S3A WS2812: real G21 RMT GRB data requires G38 driven high. Loss of that supply discards the displayed color; restoring supply alone does not restore an old frame. Supplies are ideal digital gates. No physical power key, shutdown or restart animation is invented.

INA226, LM75, RX8130, SD, CAN, RS485, buzzer, networking and physical power behavior are outside this board subset. Unsupported I2C addresses NACK. Successful generic CAN/UART driver installation does not prove an industrial interface is connected or modeled.

## Firmware evidence

The exact official factory v0.2 merged image is 5,619,252 bytes, SHA-256 `abd1a4345353ce0c166fbed6b89c3feb7d65ca2a5f37a05a34d1271405aabf2e`, obtained from the existing official M5Burner CDN entry. Its serial identifies IDF5.1.4. It boots through the full ROM to Dashboard and produces a live 240×135 framebuffer. A fresh A press/release produces `Dashboard onDestroy` and `Launcher onResume`; after fresh B/C input the guest reports `open app: LogMonitor 1`. The source defines Back as leaving Dashboard, Next as moving the launcher selection and Ok as opening it. This observed navigation sequence supports a limited application result, not all menu/function compatibility. [Factory restore instructions](https://docs.m5stack.com/en/guide/stamplc/restore_factory), [pinned application source](https://github.com/m5stack/M5StamPLC-UserDemo/tree/7fc748c3b18b7092cc482bce02c4495d3d9322e4), [observation receipt](evidence/stamplc-runtime/factory-v02.json).

The same run reports SD initialization/mount failure, RTC initialization failure and failed temperature/power-monitor initialization. Those negative results are retained. No sensor identities or successful reads were fabricated to let the application continue. The image remains trial and has not been tested on physical hardware.

The separate official UIFlow2 alternative maps to project `1897200000000001222`, v2.5.4 version `2116031314265935873`, and the exact `M5STACK_StamPLC` source target. Its M5Burner download remains subject to the historical verification boundary (`BURN_CAPTCHA_INVALID`); it is not claimed run. No exact upstream Xiaozhi target was found in the preflight audit. [Official UIFlow project](https://burner.m5stack.com/firmware/1897200000000001222), [UIFlow source target](https://github.com/m5stack/uiflow-micropython/tree/f20d5a00e8c9106aae1d944f3d6f1128839f59cb/m5stack/boards/M5STACK_StamPLC).

The independent IDF5.5.1 diagnostic source in `tools/fixtures/stamplc-firmware` is never a public/default image. Its actual-worker [receipt](evidence/stamplc-runtime/fixture.json) verifies the pixel window/backlight, three fresh button press/release cycles through PI4IO, read-clear IRQ14, front RGB, four relay GPIO readbacks, independent Stamp RGB supply, wrong address/pins/CS, shared reset, pause and platform reset. Four native board/protocol tests, native Clippy with warnings denied, catalog schemas and platform config/runtime/input tests passed. Product model and human browser interaction are audited separately. [Source download receipts](evidence/stamplc-runtime/sources.json) retain exact revisions and hashes; generated firmware and WASM stay outside Git/public artifacts.
