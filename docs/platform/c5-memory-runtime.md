# C5 physical IO_MUX and Quad PSRAM

The independent C5 interpreter now has a functional SPI0/MMU and SPI1 memory
path, plus an explicitly configured 8 MiB virtual Quad PSRAM die. This does not
turn the C5 bring-up into a complete ESP-IDF runtime. The actual rev100 ROM
still stops before the bootloader at its first unimplemented LP clock access.
Original SRAM applications can initialize this memory through real C5 MMIO.

## Sources and physical addresses

The retained [source manifest](../research/c5-memory-sources-2026-11-23/manifest.json)
contains the exact raw responses, new download timestamps, hashes and gzip
archives. Register data comes from ESP-IDF v5.5.4 commit
`735507283d5b2f9fb363a1901172dbd9e847945d`; the referenced sources are C5
`io_mux_reg.h`, `io_mux_struct.h`, `spi_mem_c_reg.h`, `spi1_mem_reg.h`,
`pcr_reg.h`, `ext_mem_defs.h`, `interrupts.h` and the C5 PSRAM controller helpers.

`io_mux_dev_t` places `gpio[29]` at offset zero. GPIO0 is physical
`0x60090000`, GPIO28 is `0x60090070`, and `0x60090074` is reserved.
The previous C5 bus and original UART fixture were shifted by one register.
They are corrected together, including the C5 LilyGO input tests. The private
`PinRoutes` storage view still uses its shared `4 + 4 * pin` convention; it is
not an extra physical address alias. The source's common register reset fields
are represented as `0x1800`; analog pad/strap electrical timing is not modeled.

The [original UART fixture](../../firmware/c5-uart-probe/README.md) is rebuilt
with corrected physical addresses. Its prior evidence files remain historical
records of their respective source and binary hashes. The new memory evidence
records the replacement ELF/bin hashes and current real guest results.

## Memory contract

| Area | Implemented behavior |
|---|---|
| Capacity | `SocBus::set_psram_size` accepts zero or 8 MiB; other sizes reject without changing the existing die |
| Native pins | CS1/GPIO15, Q/GPIO17, WP/GPIO18, HD/GPIO20, CLK/GPIO21, D/GPIO22, all selected through IO_MUX function 0 |
| Clock | Explicit nominal 48 MHz crystal and the source-defined MSPI dividers; RC_FAST, PLL and unsupported divider encodings reject accesses |
| SPI1 | CS1-only PSRAM selection; byte-aligned command, address and data phases; 64-byte FIFO and high-part bounds |
| SPI/QPI | `35h` entry, `F5h` exit, `66h` immediately followed by `99h` reset, `C0h` linear/wrap32 toggle |
| Data | SPI `03h/0Bh/02h`, Quad `EBh/38h`, and corresponding QPI operations with explicit widths and dummy counts |
| MMU | 512 entries, 64/32/16/8 KiB pages, separate flash/PSRAM target, validity and physical capacity bounds |
| AXI | SPI0 `CACHE_FCTRL.SPI_CLOSE_AXI_INF_EN` bit31 defaults closed; a guest must clear it before mapped access |
| Mapped PSRAM | Requires QPI, all native pads, `EBh/38h`, 24-bit address, six read dummy cycles, Quad phases and supported clock |
| Interrupt | Actual C5 MSPI source 44 exposes SPI1 completion and clear/enable behavior |
| Reset | Controller reset clears maps/configuration while preserving external die cells and mode; a CPU reboot also restores pad configuration |

Wrong pin routing, absent devices and ordinary wrong protocol modes return no
device response. Unsupported host encodings fault rather than pretending to
implement a different transfer. Encrypted MMU entries, DDR, ECC, octal data,
CRC-engine execution, inactive clock/reset gates and unimplemented XTS/PMS/NAND
register blocks do not expose plaintext RAM or fabricated completion.

The register metadata is generated by
`esp32c5/tools/generate_mspi_registers.py` from the retained fixed headers.
Metadata alone does not register a peripheral engine: the private MSPI wrapper
exposes only its implemented register and transaction subset. Existing shared
`SpiMem` behavior for other SoCs is unchanged.

## Explicit virtual-device choices

The protocol reference is AP Memory APS6404L-3SQR revision 2.7, sections 9–14.
The modeled die is **AP-compatible virtual 64-Mbit Quad PSRAM**, not a dump of
the undocumented production die bonded inside C5HR8. The WROOM-1/WROOM-1U
datasheet v1.3 tables 1-1/1-2 identify N32R8 modules as 8 MiB Quad devices, and
their module schematics show 48 MHz crystals. Those documents do not identify
the actual PSRAM manufacturer's production lot or serial number.

The virtual `9Fh` response is `0D 5D 42` followed by zero manufacturing bytes.
The prefix uses the fixed ESP-IDF driver's public manufacturer/KGD/density and
non-2T fields. It is not presented as an observed physical ID. ID reads follow
that driver's SPI initialization contract, which probes before its explicit
reset sequence; revision-specific EID-read timing restrictions of the AP part
are not fully implemented.

Newly allocated memory is deterministically zero for reproducible tests, not
as a physical power-on guarantee. Linear and wrap32 command bursts follow the
documented address behavior and nominal 3.3 V frequency limits. Cache access is
coherent and functional: there is no cache-line residency, serial latency,
arbitration, refresh or analog tuning model. CPU read/write/fetch use the same
validated mapping. External-memory GDMA payloads are not part of this commit.

## Executed checks and limits

The [original memory diagnostic](../../firmware/c5-psram-probe/README.md) runs
through the ordinary `Machine` SRAM app loader. The guest sets the six native
pads, does SPI and QPI round trips, opens AXI, builds all 128 MMU pages, writes
and reads all 2,097,152 words, checks byte and halfword accesses at the final
addresses, and executes `addi`/`ret` from the PSRAM mapping. It prints
`C5 PSRAM8 PASS` only after those checks.

The [current evidence](../evidence/c5-memory-2026-11-23/results.json) records
the final source and binary hashes, raw UART, dispatch/retired counts, negative
protocol tests, test logs and CPU comparison. It distinguishes the original
diagnostic from an official firmware and records the real ROM's early fault.
There is no factory UI, RF, physical-board or browser/WASM acceptance in this
memory-only checkpoint. Default C5 product memory capacities are not silently
changed by the presence of the optional memory model.
