# CoreMatrix C158 firmware source audit

The pinned official GitHub UIFlow2 image is a complete 16 MiB-layout ESP32-C61 image, SHA-256 `8d5b8d4e22ebc293937086b2f9f218aa5a5ebda27b5ccb32b3f8f580ee02939b`. The downloaded file contains 16,773,120 bytes, bootloader at 0, partition table at 0x8000 and application at 0x10000. Both ESP images declare chip ID 20, minimum full chip revision 100 and maximum 199. Segment XOR checksums and appended SHA-256 pass; the partition end fits the product's 16 MiB Flash. The application descriptor declares `ESP-IDF v5.5.4-dirty` and `V2.5.4`.

`factory-audit.json` records the separate factory/UIFlow1/UIFlow2/Xiaozhi investigation. Neither the current exact-device Burner inventory nor the official product/tutorial documents identify a distinct factory/restore image. The default remains explicitly **UIFlow2**, not factory firmware. `sources-and-image.json` records source URLs, fetch times, byte lengths, hashes, exact public project/version/device identities and image layout. The binaries are only temporarily downloaded outside the repository; none are committed or staged on the website.

M5Burner's v2.5.4 build is named `509a67aa`; GitHub's is `e437118`. They are separate catalog options. The current Burner endpoint requires a CAPTCHA (`HTTP 400`, `BURN_CAPTCHA_INVALID`); it was not downloaded and has no invented digest or inherited image checks. GitHub's range GET responds successfully but its redirect/asset responses omit `Access-Control-Allow-Origin`; this is a CORS limitation, not a missing link. Official download followed by local file import is available. No mirror or CAPTCHA bypass was used.

To reproduce source discovery, request the public URLs in the source receipt, verify the exact project is `OFFICIAL`, the supported device is `2093000000000000005` (`CORE_MATRIX`) and each selected version is `PUBLIC`/`PUBLISHED`. Review the names as well as the device category. Download the exact GitHub image URL, run `shasum -a 256 <downloaded-image>`, and use the platform's local loader after C61 integration to revalidate chip, checksums and layout. The explicit binary/source hash is the boundary for execution receipts; source metadata alone does not prove startup or peripheral compatibility.

Static validation at this stage: `node tools/check-firmware-watchlist.mjs --offline` passed. `node --test tools/platform-firmware-sync-test.mjs tools/platform-firmware-policy-test.mjs tools/platform-firmware-download-access-test.mjs` passed all 27 tests. Full catalog validation needs the concurrently integrated C158 product/chip schema. Execution and physical hardware remain unverified in these source receipts.
